# Sahaayak AI

AI-powered navigation for government services.

Sahaayak AI helps citizens describe a government-service need in natural language, find matching records from a verified service directory, understand why those services are relevant, and continue to the official portal.

## Problem

Government services are spread across many departmental websites. Citizens often know the problem they need to solve, but not the name of the service or the correct official portal.

## Solution

Sahaayak AI combines a searchable MongoDB service catalogue with a grounded AI assistant. Retrieval happens first, so the model receives only the small set of service records relevant to the request. Recommendations are linked back to real service records and their existing official URLs.

## Key Features

- Natural-language assistant at `/ai-assistant`
- Retrieval of up to five relevant services before an AI call
- Natural conversational answers with bounded session memory
- Grounded recommendations and contextual follow-up suggestions
- Server-only OpenAI Responses API integration
- Graceful grounded fallback when OpenAI is unavailable
- Existing service search, category filtering, pagination, detail pages, and official links
- Responsive React interface with verified-directory signals

## Architecture

```text
React + Vite
  | Axios through Vite /api proxy
  v
Express API
  |-- /api/categories
  |-- /api/services
  |-- /api/ai/assist
  v
MongoDB via Mongoose
  |-- Category
  |-- Service
```

The assistant flow is:

```text
User message
  -> input validation
  -> MongoDB retrieval and scoring
  -> top service context
  -> OpenAI Responses API or grounded fallback
  -> natural answer plus verified recommendations
  -> assistant UI
```

## Retrieval and Grounding

`server/services/retrievalService.js` tokenizes the request, removes common stop words, searches service name, description, keywords, eligibility, and common use cases, then ranks candidates with higher weight for name, keyword, and category matches. Only the top five records are passed to the AI service.

The AI prompt prohibits invented schemes, requirements, documents, deadlines, URLs, and procedures. Model recommendations are filtered against the retrieved MongoDB IDs before they are returned to the browser. The fallback response is also generated from retrieved records and never invents an official URL.

## Tech Stack

- Frontend: React 18, React Router 6, Vite 5, Axios, plain CSS
- Backend: Node.js ES modules, Express 4, Mongoose 8
- Database: MongoDB
- AI integration: official OpenAI Node SDK and Responses API

## Environment Variables

Create `server/.env` from `server/.env.example`:

```env
MONGO_URI=mongodb://127.0.0.1:27017/govservices
PORT=5000
OPENAI_API_KEY=
OPENAI_MODEL=gpt-4o-mini
DEBUG_RETRIEVAL=false
```

`OPENAI_API_KEY` is optional. Without it, `/api/ai/assist` uses the grounded retrieval fallback. The key is never read by the React application or sent to the frontend. Recent conversation history is kept in a bounded in-memory session store and is cleared when the backend restarts.

Set `DEBUG_RETRIEVAL=true` during development to log normalized tokens, alias expansion, phrase matches, score reasons, and final ranking. It is disabled by default and never appears in API responses.

## Installation and Running

Start MongoDB first, then:

```bash
cd server
npm install
node scripts/seed.js
npm run dev
```

In another terminal:

```bash
cd citizen-portal
npm install
npm run dev
```

Frontend: `http://localhost:3000`
Backend: `http://localhost:5000`

## Dataset Summary

The seed script contains 10 categories and 31 services. Existing service names, categories, and official URLs are preserved. Each seeded service also receives optional structured context:

- `eligibilitySummary`
- `requiredDocuments`
- `commonUseCases`

The context is category-aware and intentionally concise. Official links are not generated by the enrichment logic.

## API Endpoints

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/api/health` | API and database health |
| GET | `/api/categories` | List categories |
| GET | `/api/services` | Search, filter, and paginate services |
| GET | `/api/services/:id` | Get one populated service |
| POST | `/api/ai/assist` | Retrieve grounded services and return assistant guidance |
| POST/PUT/DELETE | `/api/services`, `/api/categories` | Existing service and category management endpoints |

Example request:

```json
{
  "message": "I lost my Aadhaar card. What should I do?",
  "sessionId": "browser-generated-session-id"
}
```

The response contains `answer`, `recommendedServices`, `followUpSuggestions`, `followUpQuestions`, `actionPlan`, `grounded`, `provider`, and `sessionId`.

For local ranking regression checks, run `node scripts/test-retrieval.js` from the `server` directory. The script covers Aadhaar, EPF/employment, passport, scholarships, cybercrime, and ambiguous requests.
For contextual follow-up checks, run `node scripts/test-conversation.js` from the `server` directory. It covers Aadhaar documents, EPF balance, passport documents, and ambiguous requests.

## Engineering Decisions

- Reused the existing service model, API conventions, and Express service layer.
- Chose transparent ranked retrieval over a vector database for this small verified dataset.
- Kept OpenAI behind a backend boundary and mapped recommendations to retrieved IDs.
- Added bounded recent-message session memory for contextual follow-up questions.
- Added optional schema fields with defaults so existing documents remain compatible.
- Preserved the existing catalogue routes and frontend workflows.

## Limitations

- OpenAI Responses API access requires `OPENAI_API_KEY`; without it, the grounded fallback remains available.
- Retrieval is lexical and ranking-based; it is not semantic vector search.
- The service directory is informational. Citizens should confirm current requirements on the official portal.
- A running MongoDB instance is required for real service retrieval.

## Future Improvements

- Add multilingual responses and language-aware retrieval.
- Add evaluation fixtures for groundedness and recommendation precision.
- Add semantic embeddings after the catalogue and evaluation set grow.
- Add source timestamps and department metadata to service records.
